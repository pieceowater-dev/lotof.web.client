# Требования владельца (сводка из чата) — рабочий документ

Источник правды по тому, что просил владелец проекта (lota.tools) в ходе работ по доработкам Menu → Issues → Goods → Contacts → Capital/Hub.
Обновлять по ходу работы: отмечать выполненное, добавлять новые замечания **дословно по смыслу**, ничего не терять. Подробные планы по сервисам лежат в `IMPROVEMENTS_PLAN.md` каждого сервиса; этот файл — про то, **как** и **в каком порядке** работать и какие правила действуют поверх планов.

## 1. Общие правила работы

- Язык общения — русский.
- Работать автономно, до отказа: не останавливаться на уточняющих вопросах, решать самому и идти дальше. Короткий отчёт в конце.
- **Не следить за деплоем** (CI/Argo не опрашивать). После пуша сообщить коммит и остановиться. Единственное исключение — проверить, что бэкенд и gateway уже на новых образах, **прежде чем пушить web** с новыми полями GraphQL.
- Порядок деплоя: proto → backend (msvc) → gateway (gtw) → web. Пушить всё можно в одну сессию, но web — только когда gateway с нужными полями уже в кластере (иначе прод ломается, как 2026-10-10).
- **Никаких `Co-Authored-By`, «Generated with Claude Code» и т. п.** в коммитах и PR. Только авторство владельца.
- **Данных нет нигде, кроме Atrace.** Во всех остальных сервисах схемы, proto, контракты и БД можно свободно мутировать/мигрировать/пересоздавать. Atrace трогать осторожно.
- Не поднимать стоимость инфраструктуры (реплики, ресурсы) без вопроса.
- Не править сгенерированные файлы руками — только перегенерация (protoc 29.3, protoc-gen-go v1.36.0, protoc-gen-go-grpc v1.3.0; gqlgen через `go run github.com/99designs/gqlgen generate`, не `make gql-gen`).
- Перед каждым коммитом в Go-репозиториях: `go build ./...`, `go vet ./...`, `go test ./...` — и **не** склеивать коммит/пуш в одну команду с ожиданием тега proto (дважды ломали сборку пушем до появления тега).
- Для web: typecheck + vitest + `nuxi build` перед пушем.

## 2. Дизайн и UX

- Весь UI строго по `lotof.web.client/DESIGN.md` (`.at-panel`, `.at-seg`, `.pill-filter`, `.at-btn`, `.at-row`, `.at-chip`, `.at-switch` + `UToggle`, стекло для виджетов и т. д.). Нативные select/checkbox, серые коробки, «слитые» зелёные кнопки — «уродливо».
- Никакого чёрного/почти чёрного акцента; только палитры (никаких сырых `<input type=color>`).
- **Тёмная тема и мобильная адаптация проверять для всего, что делаем.** Менее важные функции на мобильном можно скрывать, чтобы не захламлять экран.
- Низкий порог входа: функциональность не должна требовать менеджера/саппорта для настройки; новые возможности выключены по умолчанию и включаются настройкой/пресетом.

## 3. Цель продукта

Сделать lota функционально и по продуманности **не хуже и лучше конкурента**, сохранив низкий порог входа. Оценивать честно: если пункт плана не сделан — так и говорить.

## 4. Порядок работ

1. Довести **все** пункты планов: Menu → Issues → Goods → Contacts → Capital/Hub. В каждом сервисе проверить, что все пункты плана действительно выполнены, и только потом переходить к следующему.
2. **Telegram — в самом конце** (требует вмешательства владельца: он создаёт бота). К тому моменту подготовить **подробную инструкцию**: как создать бота (BotFather), как назвать, куда положить токен, как подключить к lota, как пользоваться, что настраивать. Telegram — выбранный канал для уведомлений/сообщений клиентам и исполнителям (WhatsApp-интеграции не будет).
3. **После всех функций — аудит ролей, ограничений и доступов по всем сервисам и модулям**: кто видит персональные данные (должна быть роль/право, при котором ПДн скрыты везде), кто может экспортировать заказы, клиентов и т. д. Всё логично и чётко, по всему проекту.
4. Проверка тёмной темы и мобильной адаптации по всему, что сделано.

## 5. Новые сквозные требования (последние сообщения)

- **S3 для файлов**: везде, где можно и нужно загружать файлы, подключить S3 в этих модулях (в некоторых модулях он уже есть — переиспользовать тот же подход/модуль `media`).
- **Лимит хранилища на приложение (per app)**: у каждого приложения свой лимит в ГБ (например, Contacts — N ГБ, Menu — A ГБ и т. д.); учёт занятого места по тенанту и приложению, проверка при загрузке, показ использования; лимит привязать к тарифам Capital (поля лимитов плана).
- **QR в документах** — не отдельная «переменная под QR», а на лету из публичной динамической ссылки: `{{QR:ПЕРЕМЕННАЯ_ССЫЛКА}}` или `{{QR:https://…}}`; переменная `ORDER_LINK` (`ЗАКАЗ_ССЫЛКА`) — публичная ссылка на отслеживание заказа. (Сделано.)
- Для действий, где нужна повторная авторизация (чувствительные), — вход через Google; пароли не храним; только Google-авторизация.
- Не делать: WhatsApp-интеграцию, глубокую матрицу прав **кроме** финального аудита ролей/ПДн/экспорта (п. 4.3).

### Результаты проверки фронта (2026-10-14)

Проверка шла на локальном стенде (16 сервисов + web) в настоящем браузере: телефон 390 px, планшет 768 px, десктоп 1440 px, светлая и тёмная темы, русский/английский/казахский, около 60 маршрутов плюс открытые модалки. Автоматически искались сырые ключи перевода, `undefined`, `[object Object]`, `{{ }}`, `{value}`, служебные даты, константы-перечисления и горизонтальное переполнение.

**Найдено и исправлено:**
- Даты в Goods показывались в отладочном формате Go (`2026-10-08 10:56:14.97892 +0000 +0000`): сервис теперь отдаёт RFC3339, web разбирает оба формата и показывает «8 окт. 2026 г., 15:56».
- У приходов, списаний, перемещений и заказов поставщику не было номера (пустая колонка «#»): теперь `PR-1`, `WO-1`, `TR-1`, `PO-1`.
- Кнопки с классом `at-btn` игнорировали `hidden`: «скрыть на телефоне» не работало ни в одном месте приложения.
- Таблицы на телефоне показывали 2–3 колонки, а статус и сумма уходили за экран: теперь каждая строка превращается в карточку. Страницы-списки больше не сжимают таблицу до одной строки (раньше в Заказах на телефоне была видна одна строка).
- Тексты заголовков таблиц, названий статусов и блоков лендингов считались один раз при загрузке на русском и не менялись при другом языке (английский и казахский видели русские заголовки). Сделано реактивным (45 мест).
- Сырые значения на экране: статус клиента (`ACTIVE`), тип контакта, статус карточки штампов, статус заказа на витрине.
- Форма «Оформить движение»: поля позиции налезали друг на друга на телефоне, кнопки уходили за экран; все модалки теперь прокручиваются внутри карточки над кнопками.
- Плитки склада обрезали большие суммы; «Console» в шапке не переводилась; сообщение «No plans token» показывалось пользователю как есть; английские тексты ошибок складских операций теперь на языке интерфейса.
- Переводы: английский закрыт полностью (был русским весь раздел «Запись»), казахский: весь Issues и «Запись» (около 770 строк). Платформенная консоль (admin) остаётся на русском.

**Не удалось воспроизвести:** «куски кода» в модалке создания заказа. В модалке на всех размерах и языках сырых ключей, констант и служебных строк нет; если встретится снова, нужен скриншот и шаги.

**Остаётся:** визуальная проверка глубоких состояний (карточка заказа/клиента/задачи с реальными данными, режим кассы, таблицы Atrace) выборочная; тёмная тема проверена автоматически на текст и переполнение, цвета контраста целиком не просматривались.
