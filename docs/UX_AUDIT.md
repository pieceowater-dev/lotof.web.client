# UX-аудит платформы lota (2026-10-14)

Правила, по которым оценивали: `DESIGN.md` (Часть I — внешний вид, Часть II — UX: поведение, пути, формы). Это **единый реестр находок**: старый `UX_PLAN.md` и отдельные аудиты влиты сюда.

**Как пользоваться.** Находки сгруппированы по приложениям, у каждой есть ID, чтобы чинить постепенно
и ссылаться в коммитах («UX M3»). Колонка «Статус»: ⬜ не начато · 🟨 в работе · ✅ сделано.
Серьёзность и трудоёмкость — по шкале из `DESIGN.md` §U16 (S1–S4; XS/S/M/L).

## 0. Метод и честные ограничения

- Аудит **по коду**: прочитаны главные страницы и ключевые модалки Menu, Issues, Goods, Contacts, Plans,
  A-Trace, Hub, плюс общие компоненты (`AppTable`, `EmptyState`, `useConfirm`, тосты, лейауты) и посчитаны
  сквозные метрики по всему репозиторию (grep). Приложения **не открывались в браузере**: визуальные и
  «ощущенческие» вещи (скорость, плотность, касания) нужно подтвердить глазами — они помечены «проверить».
- **Не покрыто или поверхностно:** Console (владельческая админка), публичные витрины и страницы
  отслеживания `/to/:ns/*`, Гид, Chekalka, POS-касса (`goods/register`, 1172 строки), Zen-режим целиком,
  настройки (кроме количества вкладок). Это следующий заход; начинать лучше с POS и публичной витрины.
- Оценки «кликов до цели» — по коду, не по хронометражу.
- Серьёзность выставлена исходя из того, что основной пользователь — сотрудник малого бизнеса,
  работающий часами, часто с телефона (см. гайдлайн §0).

## 1. Что взято из прежнего плана (`UX_PLAN.md`, удалён)

Семь принципов (телефон — полноценный клиент, один главный способ, видимые состояния, язык человека, не терять ввод, одинаковые детали, подвал не мешает) вошли в `DESIGN.md` Часть II. Удачные решения, которые стоит **тиражировать**: композер комментария в ленте заказа, «Новый товар» прямо в форме прихода, вложенные окна без потери родителя, «Исправить» проведённый документ, быстрые представления над доской, «Отказаться» с причиной у курьера, панель переходов в карточке клиента. Чего не хватало плану и что добавлено: понятие «пути» (сколько действий до цели), роле-ориентированная навигация, отмена действий, состояние в URL, критерии пустых состояний, выбор клиента между приложениями.

## 2. Что в платформе уже хорошо (сохранять)

- Единая дизайн-система и пилюльные фильтры; скелетоны вместо спиннеров (~60 мест); `AppTable` сам
  превращается в карточки на телефоне и показывает скелет.
- Инлайн-смена статуса заказа прямо в строке списка; на телефоне — отдельный экран «Мои заказы» с
  кнопками «Позвонить» и «следующий статус» (`menu/mine.vue`) — образец полевого экрана.
- Быстрое создание задачи в первой колонке доски (заголовок + Enter), причина при переносе в
  терминальный статус, Zen-режим.
- Склад: черновики документов, «быстрый поставщик», «быстрый товар», исправление/отмена вместо удаления,
  инвентаризация по штрихкоду.
- Настройки Menu/Contacts/Plans/Goods/Issues/Atrace держат активную вкладку в URL (`?tab=`).
- Контакты: адрес с пагинацией в пути, правка имени/телефона по месту, баннер «есть обновления».
- Первые шаги в Plans («Добавьте первую услугу»), полноэкранный мастер первой локации в A-Trace.

## 5. Menu — заказы

**Задачи (Jobs):** (1) принять и оформить заказ; (2) увидеть, что горит; (3) провести заказ по статусам и принять оплату;
(4) найти старый заказ; (5) исполнитель — «мои заказы» с телефона.

**Пути (оценка по коду):** принять заказ = Хаб → Orders → «Создать» → тип, телефон, позиции → «Создать» ≈ 4 шага + ввод (хорошо, но руками
вводится клиент, X6). «Что горит» = плитки-фильтры сверху (хорошо, но их слишком много, M1). Найти заказ = поиск (по телефону/имени/номеру — хорошо).

### 1. Menu — заказы

#### Путь 1. Принять заказ по телефону

**Happy path (сейчас).**
1. Хаб → плитка Orders (1) → страница заказов.
2. «Создать заказ» (2) — кнопка последняя в строке фильтров, не в шапке.
3. Окно: выбрать тип (доставка/самовывоз/зал) (3) → ввести телефон (4) → имя (5) → адрес, если доставка (6) → филиал (7)
   → выбрать позиции кликом по списку справа (8…) → «Создать» (последний).
   ≈ 8–10 действий, из них клиент и адрес — полностью руками.

**Где застрянет / лишнее.**
- Клиент не подбирается из Контактов: постоянный клиент вводится с нуля, история не видна на приёме.
- Порядок «кто → что»; оператор на звонке чаще слышит «что» первым.
- Список позиций — одна плоская лента (`max-h-60`) без категорий и «часто заказывают».
- «Создать» неактивна без объяснения, чего не хватает.
- Случайное закрытие стирает весь ввод; черновика нет.
- После создания не ясно «что дальше» (оплатить? назвать цену? открыть?).

**Ошибки.** Невалидный телефон — подсказка под полем (хорошо). Нет филиала при самовывозе — молчаливая блокировка.
Сервер вернул ошибку — тост; ввод сохраняется (проверить).
**Загрузка.** Позиции: текст «Загрузка…» (не скелет). **Пусто.** «Нет позиций» без кнопки «добавить» (но есть «Новая позиция» сверху). 
**Первый запуск.** Мастер брендинга для владельца (есть, хорошо); у оператора до первого заказа каталога может не быть — путь тупиковый.

#### Путь 2. Сменить статус
Список: клик по бейджу статуса → меню → выбор = **2 клика**, без отмены (хорошо, что инлайн). На `/mine` — кнопка «следующий статус» = **1 тап**, но экран только для телефона-чипа. Фильтры отсекают заказ после смены — он «исчезает» из списка без объяснения (проверить).

#### Что с оплатой
Сумма оплаты и «получено наличными» видны в таблице позиций в карточке; точный путь «принять оплату» в этом заходе до конца не прослежен (**проверить**).

### 2. Issues — задачи и доставка

#### Путь 3. Быстро завести задачу
Доска → «Создать» внизу первой колонки (1) → заголовок + Enter (2) — создаётся **с приоритетом 1, без исполнителя и срока**. Дальше: открыть карточку (3) → исполнитель (4) → срок (5) → закрыть. Быстро заводить хорошо; **«быстро и сразу раздать» нельзя**.

#### Путь 4. Подробная задача / доставка
Шапка «Создать» → окно из ~8 полей: название*, тип*, приоритет, исполнитель, срок (native `datetime-local`), оценка, сумма сделки, описание, **свёрнутый «Контакт»** (имя, телефон, адрес, пин на карте).
Для доставки — адрес и телефон главные, а они спрятаны. Клиент — свободный текст; связать с Контактами можно только **после** создания (виджет в карточке). Сложные доски (спринты, воронка) добавляют поля.
**Застрянет:** непонятно, чем «Создать» отличается от «Создать из шаблона»; на телефоне окно из двух колонок полей тесное.

#### Путь 5. Исполнитель меняет статус
Zen-режим: карточка → «Позвонить / Навигатор / следующий статус / Проблема» — **образцовый полевой экран** (1 тап до результата, очередь при плохой сети: счётчик «ожидают»).
Доска на телефоне: колонка на 85% ширины, перетаскивание не работает пальцем (HTML5 drag) → открыть карточку → статус = 3 касания.
**Пусто:** Zen — «нет открытых задач» (хорошо). **Ошибка:** гео запрещено — статус виден (хорошо).

### 3. Goods — касса и склад

#### Путь 6. Продажа на кассе (POS)
1. Открыть смену: ввести остаток в кассе (1–2) — обязательный шаг утром.
2. Поиск/скан в одном поле (Enter) — товар сразу в корзину; карточки товара по категориям (1 тап).
3. «Оплатить» наличными/картой — **1 тап**; подарочный сертификат — окно с кодом.
Хорошо: скан-первым, количество +/−, корзина с итогом внизу.
**Открытые вопросы (бизнес-логика, не придумывать):** нет ввода «получено» и расчёта сдачи; нет предложения чека/печати (в коде `receiptPrinterEnabled: false` — аппаратная настройка?); в шапке до 7 кнопок (склад, X-отчёт, внесение/изъятие, история, возврат, закрыть смену) — на телефоне это ряд из мелких кнопок.
**Ошибки:** сбой оплаты — тост, корзина остаётся (хорошо). Потеря сети — **не обработана** (проверить).
**Первый запуск:** «нет кассы → Создать кассу» для владельца, у кассира — тупик без подсказки.

#### Путь 7. Приём товара
Склад → Движения → «Создать» (1–3: вкладка + кнопка) → окно: тип из 5 (1) → склад (2) → поставщик (3, либо «+») → позиции (по каждой: товар, количество, цена, партия) → «Сохранить».
≈ 7 действий + позиции; **скан-ввод позиций прихода** — по коду только в инвентаризации (проверить в `MovementItemBuilder`).
Хорошо: черновики, «Новый товар»/«Новый поставщик» прямо в форме. Плохо: из «мало на складе» путь к закупке — через эти же 7 шагов.

#### Путь 8. Завести товар
Одно окно, **обязательных 3** (название, единица, цена) + трекинг остатка — образец минимализма. Нет «Сохранить и добавить ещё» (при заведении 50 позиций — 50 открытий окна). Штрихкод отдельным полем в форме не найден — при скане поиск идёт по SKU (**вопрос владельцу**).

### 5. Plans — запись

**Застрянет:** слоты появляются только после услуги и даты (нет подсказки «сначала выберите услугу»); нет «ближайшее свободное окно».

### 2. Как должно стоять (эталон, сжато)

Полный текст — `DESIGN.md` §5. Для разбора ниже:
1. **Порядок = порядок мысли**: кто → что → когда → сколько. Обязательное сверху, необязательное под «Ещё».
2. **Подпись над полем**, placeholder — пример значения. Обязательность — одним способом (`required`).
3. **Действия** формы: главное справа/внизу и видно без прокрутки (на телефоне — прилипшая нижняя панель),
   «Отмена» — слабее; подпись главного — глагол+объект.
4. **Enter** отправляет, Esc закрывает с защитой, клавиатура телефона показывает «Далее/Готово».
5. **Сохранение** одной из трёх моделей на тип экрана (F2), всегда с видимым состоянием «Сохранено».
6. **Тип поля = тип данных**: деньги — числовое поле с десятичной клавиатурой; даты — с пресетами;
   ≤ 4 варианта — сегмент, а не выпадающий список; клиент — подбор, а не текст.

### 5. Что менять и в каком порядке (решение, шаг 3)

#### Варианты

**A. Точечная полировка.** Править каждую форму руками по этому списку.
+ Быстро видны результаты; нет нового кода-основы. − 98 модалок × разные правки; через месяц снова разъедется; F1/F2/F6/F13 не решаются.

**B. «Набор форм» + миграция горячих путей (рекомендую).** Общие примитивы, затем перенос форм по приоритету:
`FormModal` (оболочка: `<form>`, Enter/Esc, подвал, прилипшая панель, защита от закрытия, ошибка→фокус),
`Field` (подпись/обязательность/подсказка/ошибка, `autocomplete`/`inputmode`/`enterkeyhint`),
`MoneyField`/`QtyField`, `DateField`/`DateRangeField` с пресетами, `SegmentedField`, `ClientPicker`,
`SaveBar`/индикатор «Сохранено». + Закрывает F1–F6, F10–F18 сразу и навсегда; новые формы собираются из готового. − 2–3 недели до видимого результата; нужен аккуратный перенос без поломки логики.

**C. Переосмысление потоков.** Пошаговые мастера для заказа, записи, клиента (на телефоне — экраны по одному вопросу).
+ Лучший мобильный опыт. − Дольше всего; для опытного оператора шаги медленнее одной формы; меняет бизнес-логику сценариев.

**Рекомендация: B, затем элементы C только на 3 горячих путях на телефоне** (заказ: позиции → клиент;
запись: услуга → время → клиент; клиент: телефон → имя). На десктопе остаётся одна форма.

#### Доступность, учтённая в выборе
- Подпись всегда над полем (экранные читалки, автозаполнение), ошибка связана с полем (`aria-describedby`).
- Тап-цель ≥ 44 px для слотов времени, +/−, плиток типа (сейчас `xs`-кнопки).
- Фокус: видимое кольцо, возврат в вызвавший элемент при закрытии окна, Esc.
- Клавиатура: Enter/Esc/⌘Enter; на телефоне `enterkeyhint` и числовые раскладки.
- Контраст: состояния не только цветом (ошибка — текст + иконка).

#### Порядок внедрения (если идём по B)
1. `Field`+`FormModal`+`SaveBar` (F1, F2, F3, F6, F13, F14) — перенести 5 горячих форм: заказ, задача, запись, товар, клиент-быстро.
2. `ClientPicker` (F18) в заказе, записи, задаче; подключить быстрое создание клиента вместо мёртвого `ClientCreateModal`.
3. `MoneyField`/`DateField` (F10, F15, X9) — фильтры заказов, касса, приход.
4. Точечно: F9 (подтверждение платежа) — **можно сделать сразу, отдельным маленьким коммитом**.
5. Остальные формы мигрируют по мере касания.

### 6. Что проверить глазами (не покрыто)
- 390 px, тёмная тема: заказ, запись, касса, настройки Plans.
- Реальная скорость Enter/Tab-порядка в заказе и товаре.
- Поведение клавиатуры iOS/Android в кассе и PIN-полях.
- Публичные формы витрины и записи клиента (`/to/:ns/*`) — не аудировались.
